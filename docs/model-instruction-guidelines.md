# 模型指令编写原则

本文供维护者修改模型实际可见的内容及其加载方式时使用。目标是让模型在需要时获得清晰、足够、能指导行动的信息，减少重复提醒和无实际用途的流程负担。

范围包括 MCP 宿主、内部 pi durable 协调者和 ACP 执行端收到的本项目内容：角色提示、工具与字段说明、动态任务状态、节点派发、任务记忆、历史摘要、启动引导、通知、技能、参考资料和模板。当前入口见[模型上下文导航](technical-design.md#模型可见上下文)。

## 从实际上下文出发

以宿主或 SDK 实际组装的内容判断取舍，尤其检查宿主新会话的第一次任务、协调者首次处理 Task，以及节点第一次 ACP 派发。同时考虑原生提示、用户资料、工具声明、技能目录、历史和动态状态，避免只看某个 Markdown 文件或提示常量。

宿主会话、协调会话和节点会话分别组装上下文，不能假定一处可见的资料已传到另一处。确认接收者实际需要什么，再决定由固定提示、工具契约、派发上下文或按需读取提供。

每段指令应有具体用途：它帮助模型作什么决定、执行什么操作，或者避免什么已知错误。根据用途保留、合并、删除、条件加载或按需读取，不以字数最少为目标。没有明确需求的规则不要因为“看起来更严谨”而加入。

## 直接说明要做什么

使用自然、直接的语言，写清职责、操作入口、参数含义和下一步。内部架构与执行机制只在改变实际操作时说明，其余留在开发文档。

例如，向节点提供工作要求、必要背景、资料引用和交付要求即可，无须展开业务账本、SDK 检查点和 worker 的内部关系。Task 与 Run 的区别、状态、分页、问题回答、通知及异步完成等含义会影响工具调用，应在相应契约中保留必要细节。

## 不增加泛化流程

按用户请求和已有约定推进，不自行补入通用的证据收集、授权核对、审批、独立复核或业务验收流程。不在角色、工具、技能和通知中反复写“不扩大授权”“不等于成功”等提醒，也不为普通交付固定证据报告或复核结论格式。

具体任务需要查来源、复核计算或检查结果时，写明实际要检查什么。专业方法可以保留影响结果的口径、假设、数据处理和适用条件；常规操作不因此变成逐项审批或留证任务。独立复核按用户需求或具体问题安排，不设为默认必经步骤。

本项目的节点交付验收与整体完成判断是协调者已有职责，执行准入、事实提问、补充意图和不确定结果阻断也有明确业务契约，见[会话设计](task-conversation-plan.md)。围绕这些决定提供必要说明，按节点目标审查交付；不因此增加默认审计节点、用户逐项批准或统一交付模板。普通文本和 Markdown 可以作为交付，格式要求由任务决定。

权限和确认机制沿用宿主、执行端原生配置、凭据、外部服务及用户约定。不要为假设风险新增提示门槛，也不要通过提示掩盖或绕过实际执行限制。保留直接影响操作的事项，如配置作用域、凭据引用、内容公开范围，以及结果未知时先查状态、避免重复执行。业务限制由实际服务入口执行，提示帮助模型正确使用这些入口。

## 保留实用细节，按用途放置

| 内容 | 放置要求 |
| --- | --- |
| 首次任务就需要的职责与资料位置 | 放在对应角色、服务引导或首轮上下文中 |
| 工作目录用途、资料组织与模板导航 | 在首次需要使用的会话中可见，不能只藏在尚未选择的维护技能里；已有用户布局与约定优先 |
| 工具参数、分页、状态和结果入口 | 放在工具契约中，避免其他提示重复完整说明 |
| 节点背景、选定用户事实、上游和旧交付 | 按本轮工作提供；相关补充或澄清说明仅在对应情形加入，完整资料按引用读取 |
| 安装、维护、执行端接入和任务使用方法 | 通过技能或参考资料按需读取，正文包含能实际执行的方法和必要细节 |
| 动态状态、启动异常、后台通知与工具错误 | 提供当前操作需要的字段和下一步；详细诊断留在状态或日志入口 |
| 任务记忆与历史摘要 | 记忆保留后续判断需要的事实、来源及适用条件；历史压缩沿用 SDK，定制摘要时使用专用提示与待总结资料，不混入普通工作角色和无关技能 |

优先使用宿主和 SDK 已有的资源发现、技能、工具、配置和上下文去重机制。检查同一要求是否已由原生提示或其他已加载内容提供；专用说明不要无条件叠加到所有会话。已经完整可见的内容无需为了固定流程再次查询，截断或缺失的资料应保留读取入口。

## 在正确位置修复

先区分提示内容、上下文组装、功能实现和测试问题。加载缺失、时序错误、重复注入或错误处理问题应修代码；不要增加提示规则来补偿。

发现一类问题后，检查相关的宿主、协调和节点入口，包括代码生成的任务、通知和工具结果。共享内容变化时检查使用它的各宿主适配；复查既有处理是否过度定制，不为单个案例继续叠加规则。

修改本项目维护的内容与加载逻辑，保留用户资料、角色补充、历史和备份。不要为了整理提示而迁移用户布局、覆盖用户约定、改写固定 DAG 或改变既有执行合同。

## 验证与记录

加载和组装行为用真实宿主 SDK、本地文件和进程检查来源、首轮出现时机、后续更新、条件加载及去重。测试应覆盖具体行为，不能断言提示句子、标签或全文快照；不能为了满足文案断言反向修改提示，也不为纯文案调整新增此类测试。结构化输入输出可以作为逻辑契约验证。

运行适用的[仓库检查](../AGENTS.md#风格与命令)，加载行为有实质变化时更新[代码导航](technical-design.md#模型可见上下文)或对应设计说明。字符数只能说明文本长度变化；本地加载检查不证明模型理解、交付判断或费用改善。真实模型效果按实际验收范围记录在[验证说明](validation.md)，不追加提示调试流水账。
